# Fuji PTP ecosystem research: prior art and improvement candidates

Research date: 2026-08-31. This document cross-references this repository's own physical-device findings (X-T5, PTP firmware 4.31, USB mode 0x6 "USB RAW CONV./BACKUP RESTORE") against the two most complete open-source Fuji PTP implementations (`libgphoto2`'s `camlibs/ptp2` and `petabyt/libfuji`), the Fuji WiFi/RE community, macOS PTP-claiming practicalities, and the current state of the relevant Rust crates. Every claim below is marked VERIFIED (read directly in the cited primary source, with a link) or INFERRED (my reasoning from VERIFIED facts). Where a source could not be fetched or did not contain the needed detail, that is stated rather than guessed.

## Summary

`libgphoto2`'s Fuji PTP support (`camlibs/ptp2/ptp.h`, `library.c`, `ptp.c`) is the most complete open catalog of Fuji device-property names in wide use, but it has no knowledge of the "USB RAW CONV./BACKUP RESTORE" object-exchange payloads, the "Still"/"Live" virtual stores, or a working RAF backup/restore transfer, and several properties this repository observed on the physical X-T5 (D17B, D189, D1A5, D208, D18C) remain nameless there too. `petabyt/libfuji` (2026, active) is a much closer match to this repository's own reverse-engineering: it names the RAW-conversion property family (D183/D184/D185/D186/D187), documents `USBMode` (D16E) with the exact values 5/6/8 this repository captured, and ships a `d185.c` parser plus seven committed binary captures, three of them labeled as X-T5 payloads. Byte-level decoding of those captures (done directly in this session, see Q2) both confirms and contradicts specific values this repository's FML currently declares as `unverified` for the X-T5 raw-conversion profile — this is the single highest-value finding below. macOS's `ptpcamerad`/`PTPCamera` device-claiming behavior is a long-documented, still-unsolved nuisance across the whole `libgphoto2`/darktable/digiKam ecosystem, with no supported way to disable it permanently; `libusb_reset_device`'s own documentation does not mention the device-drops-off-the-bus behavior this repository observed, which appears to be an undocumented macOS/XHCI quirk rather than a known libusb limitation. On the Rust side, `binrw` 0.15.2 (current) is already adopted per `docs/internals/binrw-ptp-migration-research.md`, so no action is needed there; `rusb` 0.9.4 is the crate's current release but the project itself has not published since April 2024, while `nusb` is pure-Rust, actively maintained (updated within the last month), and offers both blocking and async APIs on macOS via IOKit — a genuine, if non-trivial, migration candidate for `src/lib`'s transport layer.

## Q1: libgphoto2's Fuji property/opcode knowledge

**Source**: `gphoto/libgphoto2`, `camlibs/ptp2/{ptp.h,library.c,ptp.c,config.c}` at `master`, fetched directly via `raw.githubusercontent.com` in this session (VERIFIED, read in full).

- VERIFIED: `PTP_VENDOR_FUJI` is `0x0000000E` ([ptp.h:203](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)).
- VERIFIED: `libgphoto2` names 208 `PTP_DPC_FUJI_*` device properties in `ptp.h`. The ones this repository's device run observed with values all resolve cleanly: `D001` = `FilmSimulation`, `D007` = `DRangeMode`, `D008` = `ColorMode`, `D00A` = `ColorSpace`, `D00B`/`D00C` = `WhitebalanceTune1`/`2`, `D017` = `ColorTemperature`, `D018` = `Quality`, `D01C` = `NoiseReduction`, `D023` = `GrainEffect`, `D029` = `Shadowing`, `D104` = `BlackImageTone`, `D186`/`D187` = `TetherRawConditionCode`/`TetherRawCompatibilityCode`, `D20B` = `DeviceName`, `D212` = `CurrentState`, `D320`/`D321` = `HighLightTone`/`ShadowTone`, `D34D` = `LMOMode`, `D36A`/`D36B` = `BatteryInfo1`/`2`. The FilmSimulation value 1 and GrainEffect value 6 also line up with `config.c`'s lookup tables (`fuji_filmsimulation[]` value `1` = "PROVIA/Standard", `fuji_graineffect[]` value `6` = "Off Large" — [config.c:1965](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/config.c), [config.c:1531](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/config.c)), which cross-validates this repository's own captured values against an independent source.
- VERIFIED: `D02E`, `D030`, `D031`, `D032`, `D17B`, `D183`, `D185`, `D189`, `D1A5`, `D208`, and `D18C` have **no** symbolic name anywhere in `libgphoto2`'s `ptp.h`. `library.c`'s device-info merge code adds several of these to the queried property list as bare hex literals with only a comment ("seen on xt3"), e.g. `di->DeviceProps[...+59] = 0xd17b; /* seen on xt3 */` and `...+4] = 0xd21c; /* Needed for X-T2? */` ([library.c:379-450](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/library.c)). This matches this repository's own "unmodeled" list closely — `libgphoto2` has *observed* these properties on X-T3 but never assigned semantics to them either, so they were not a gap unique to this repository's capture.
- VERIFIED: `library.c` explicitly names the mode this repository calls "USB RAW CONV./BACKUP RESTORE": a model-table comment reads `/* USB Raw Converter/Backup Restore mode, firmware version 1.20 or newer */` next to the X-E3 USB PID entry ([library.c:2724](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/library.c)), and firmware-version gating is a recurring pattern in that table (e.g. X-Pro2 "with new updated firmware 4.0", X-T2 "with new updated firmware 1.1"). `libgphoto2` does not, however, implement any object transfer, property read, or capability specific to that mode — there is no code path that switches into it, reads/writes a backup blob, or exposes the "Still"/"Live" virtual stores. Searches of `library.c` for `"Still"`, `"Live"`, `storage`, `backup`, `restore`, and the bare object-format code `0x5000` in a Fuji context returned no matches (VERIFIED negative result).
- VERIFIED: how `libgphoto2` handles a Fuji camera that answers `GeneralError` to some property queries: it does not special-case this. `ptp_fuji_getdeviceinfo()` (`PTP_OC_FUJI_GetDeviceInfo`, opcode `0x902B`) is used when supported to replace the generic, 72-entry hardcoded property list with the camera's own declared list ([ptp.c:5845](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.c)); there is no fallback logic that tries `GetDevicePropValue` after a `GetDevicePropDesc` failure, matching the "reads work for 58 of 61, descriptions fail for all 61" asymmetry this repository observed but does not explain it. `ptp_fuji_getevents()` polls `GetDevicePropValue(0xd212)` (`FUJI_CurrentState`) as an event-list substitute in normal tethering mode ([ptp.c:5879](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.c)) — i.e. `libgphoto2`'s own workaround for Fuji's PTP-event scarcity is to poll D212, which is a candidate technique if this repository ever needs event-like behavior outside mode 0x6 (mode 0x6 itself reported zero events in this repository's capture, so this technique does not directly apply there).
- VERIFIED: `0x900C`/`0x900D`/`0x901D` are defined in `libgphoto2`'s `ptp.h` only as **Leica** (`PTP_OC_LEICA_GetDebugBuffer`, `PTP_OC_LEICA_DebugCommandString`) and **Sigma** (`PTP_OC_SIGMA_FP_ClearImageDBAll`) opcodes at the same numeric values ([ptp.h:911-921](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)) — PTP vendor-extension opcodes are only meaningful within their own vendor's extension ID, so this is a coincidental numeric overlap, not evidence of shared semantics. `libgphoto2` has no Fuji-specific name or handler for these three opcodes at all. `0x9801`-`0x9805` are the standard MTP object-property opcodes (`PTP_OC_MTP_GetObjectPropsSupported` etc., [ptp.h:736-740](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/ptp.h)), consistent with this repository's "USB CARD READER" mode looking like standard PTP/MTP.
- VERIFIED: this repository's model-PID mapping is corroborated — `library.c`'s model table lists `{"Fuji:Fujifilm X-T5", 0x04cb, 0x02fc, PTP_CAP|PTP_CAP_PREVIEW}` ([library.c:2754](https://github.com/gphoto/libgphoto2/blob/master/camlibs/ptp2/library.c)), matching idVendor 0x04cb / idProduct 0x02fc.

## Q2: Other open-source Fuji projects

### petabyt/libfuji (2026, actively maintained) — the strongest independent corroboration

**Source**: `petabyt/libfuji` on GitHub, `README.md`, `docs/usb.md`, `docs/dev.md`, `lib/fujiptp.h`, `fp/README.md`, `fp/src/d185.c`, and the committed binary captures under `fp/d185/`, all fetched directly in this session (VERIFIED, read in full). This is a maintained open-source library, not a blog summary; where I additionally cite `danielc.dev` below it is explicitly the original author's own reverse-engineering writeup, called out as such.

- VERIFIED: `libfuji`'s README states it "implements support for: Wireless communication mode (Xapp/Camera Connect), Legacy and secure Bluetooth pairing modes, PC Autosave mode, Wireless tether shoot/USB tether shoot (X Acquire), Raw conversion mode (Raw Studio)" ([README.md](https://github.com/petabyt/libfuji/blob/master/README.md)) — i.e. it explicitly targets the mode this repository calls mode 0x6, associating it with Fujifilm's official "X Raw Studio" desktop app.
- VERIFIED, direct byte-for-byte match with this repository's own capture: `docs/dev.md` names mode 0x6 `FUJI_FEATURE_RAW_CONV`, described as `'USB RAW CONV./BACKUP RESTORE'` — the exact on-camera menu string this repository's own established facts record — and lists its documented capabilities: "Upload RAF images to the camera over USB; Use the camera's image processor to process images; Process the final image into a JPEG; Backup and restore all camera settings" ([dev.md](https://github.com/petabyt/libfuji/blob/master/docs/dev.md)).
- VERIFIED: `lib/fujiptp.h` defines `enum FujiUSBModes { FUJI_USB_MODE_TETHER = 5, FUJI_USB_MODE_RAWCONV = 6, FUJI_USB_MODE_WEBCAM = 8 }`, directly above `#define PTP_DPC_FUJI_USBMode 0xd16e`, with a doc comment: "value is 5 when in tether shoot mode, 6 in raw conv mode, 8 for x webcam mode" ([fujiptp.h:296-305](https://raw.githubusercontent.com/petabyt/libfuji/master/lib/fujiptp.h)). This is an exact, independent match for this repository's `fml/option.cue` `usb_mode` option (`prop_code: 0xD16E`, `raw_conversion: 0x6`) and for the mode-0x6 device run — strong corroboration that D16E is correctly modeled today.
- VERIFIED: `fujiptp.h` names `0x900C`/`0x900D`/`0x901D` as **Fuji-specific**, not coincidental Leica/Sigma overlaps: `PTP_OC_FUJI_SendObjectInfo = 0x900c` ("able to create a file"), `PTP_OC_FUJI_SendObject2 = 0x900d` ("Appears to be the same or very similar as 901d"), `PTP_OC_FUJI_SendObject = 0x901d` ("write to file"), with `docs/dev.md` noting these three opcodes were "found in an old FPUPDATE.DAT update utility" and can upload `AUTO_ACT.SCR` and `FPUPDATE.DAT` files to the SD card, something normal `SendObject`/`SendObjectInfo` cannot do. This directly explains why these three ops are advertised in mode 0x6's `GetDeviceInfo` operations set: they are the write-side of a bulk object/file upload family, consistent with mode 0x6's stated "backup and restore" and "upload RAF images" capabilities.
- VERIFIED: `fujiptp.h` names the RAW-conversion property family this repository's established facts flagged as unmodeled: `PTP_DPC_FUJI_StartRawConversion = 0xD183`, `PTP_DPC_FUJI_IOPCode = 0xD184`, `PTP_DPC_FUJI_RawConvProfile = 0xD185`, `PTP_DPC_FUJI_TetherRawConditionCode = 0xD186`, `PTP_DPC_FUJI_TetherRawCompatibilityCode = 0xD187` ([fujiptp.h:322-327](https://raw.githubusercontent.com/petabyt/libfuji/master/lib/fujiptp.h)). It also names `D02E` = `FUJI_WideDynamicRange`, `D02A` = `ExposureIndex`, `D02B` = `MovieISO`, and aliases `D212` as `PTP_DPC_FUJI_EventsList_D212` and `D21C` as `PTP_DPC_FUJI_UnknownD21C` (a name assigned to the code, but the comment still marks the *semantics* unknown).
- VERIFIED (negative result, same as `libgphoto2`): `D17B`, `D189`, `D1A5`, `D208`, and `D18C` have **no** definition anywhere in `libfuji`'s `fujiptp.h` either — confirmed by direct grep of the full file. This means this repository's own naming of `D18C` as "Custom Setting Slot" (`fml/option.cue:229`, values `c1`-`c7` = `0x1`-`0x7`) and its treatment of `D16E`/others is, for at least `D18C`, an independent contribution beyond what either major open-source Fuji PTP project has published — worth flagging clearly as this repository's own reverse-engineering result rather than something to "catch up" to a prior-art source on.

### The FP1/D185 profile format — a directly actionable finding against a real X-T5 capture

`petabyt/libfuji`'s `fp/` subdirectory is a dedicated "Fujifilm Profile parser": "Parser, validator, and converter for Fujifilm profile formats... used by X Raw Studio, mainly the raw data structure sent over PTP/USB... obtained through black-box reversing with [vcam]" ([fp/README.md](https://github.com/petabyt/libfuji/blob/master/fp/README.md)). It ships `fp/src/d185.c`, a full parser/serializer for the D185 payload, and — critically — seven committed binary captures under `fp/d185/`, **three labeled `xt5_d185_*`** (i.e. captured from an X-T5, the exact camera model this repository's own device run used), plus X-H1 and X-Pro3 samples.

VERIFIED, from `d185.c` ([fp/src/d185.c](https://raw.githubusercontent.com/petabyt/libfuji/master/fp/src/d185.c)) and confirmed by direct byte-level parsing of all seven capture files in this session:

- The D185 struct always begins with a `u16` property count, then a `u8` string-length byte, then the "IOP code" as UTF-16LE characters (one `u16` per character, no BOM), then a `u16` NUL terminator, then zero padding, then the property values as `u32` little-endian, one per declared property.
- On the write side (`fp_create_d185`), the code accumulates through this variable-length header and then **pads with zero bytes in a loop until the absolute byte offset reaches `0x201` (513)** — i.e. property values always start at a *fixed absolute offset*, not a fixed *padding length*. On the read side (`fp_parse_d185`), the offset is simply hardcoded to `0x201` after the loop, discarding whatever offset the variable-length string parsing actually reached.
- Direct parsing of the three `xt5_d185_*.bin`/`xt5_d185_3_to_host` captures (done in this session with a small Python script against the raw bytes) shows: property-value data begins at byte offset `0x201` (513) in all three files, exactly as the code predicts; the embedded IOP/profile code decodes as the ASCII string **`"FF129504"`** (8 hex characters) in all three X-T5 files (and `"FF129506"` for X-H1, `"FF159503"` for X-Pro3 — i.e. this code appears to be a per-model constant, all 8 hex characters long across every sample in the repository); two of the X-T5 files are 629 bytes with a 29-entry property count field, and one ("initial", 601 bytes) has a 23-entry property count field with the string-length byte one less than the write-side convention (8 vs 9), suggesting the from-camera and to-camera payload shapes are not byte-identical in field count, not just in total length.

This produces a concrete, checkable discrepancy against this repository's own FML: `fml/camera.cue`'s `x_t5-4.31-raw-layout-unverified` declares `profile_code: "ff179502"` and `header_padding: 0x1ee` (494) for both `read` and `write`, with `declared_field_count: 29` and `total_length` 625 (read) / 629 (write), all still `evidence.status: "unverified"`. Against the real captures:

- The `total_length: 629` for `write` matches the two 629-byte `xt5_d185_2.bin`/`xt5_d185_to_cam`-style captures exactly (VERIFIED byte count match).
- The declared `profile_code` `"ff179502"` does **not** match the profile code embedded in any of the three real X-T5 captures, which all decode to `"FF129504"` (VERIFIED via direct parsing). It is close in digit count and structure but not identical (`179502` vs `129504`). This also does not exactly match this repository's own established-fact reading of property D184 via `GetDevicePropValue`, recorded as the PTP string `"F179502,FA179502"` (a comma-separated pair, and 7 characters per code, not 8) — so there are now **three different candidate values** for what is presumably the same or a closely related identifier (`fml`'s `"ff179502"`, this session's own D184 read `"F179502"`/`"FA179502"`, and `libfuji`'s captured D185-embedded `"FF129504"`), which cannot all be correct for the same camera/firmware and needs a fresh physical-device capture to resolve.
- Recomputing `libfuji`'s fixed-offset algorithm for an 8-character profile code (the length observed in every real capture, and the length of the repository's own declared `"ff179502"`) gives a padding-loop length of `0x201 - (2 + 1 + 8*2 + 2) = 0x201 - 21 = 492 = 0x1EC` bytes, not the `0x1EE` (494) currently declared in `fml/camera.cue`. `0x1EE` is the value that algorithm produces only for a **7-character** profile code. This is a concrete, arithmetic (not speculative) mismatch between the repository's declared constant and an independently reverse-engineered, camera-matched construction algorithm.

## Q3: macOS PTP practicalities

- VERIFIED (official `gphoto2`/`libgphoto2` FAQ and issue tracker): the standard, long-documented remedy for macOS's Image Capture framework auto-claiming a PTP camera is `killall PTPCamera`, which must be repeated every time the camera is reconnected or power-cycled; "Each camera is opened with a separate instance of the PTPCamera application," so with multiple cameras attached one may need to kill individual PIDs rather than all of them (`gphoto.org` FAQ, and [libgphoto2#205](https://github.com/gphoto/libgphoto2/issues/205)). This matches this repository's own established fact about needing to kill the claiming process before opening the device.
- VERIFIED (Apple Community thread, user reports rather than an Apple document — flagged as such): on macOS Ventura (13) and later, the responsible process moved to `ptpcamerad`, which launches lazily "once an application (like Preview.app or Dropbox) wants to talk to a camera" rather than always-on, and restarts itself if the triggering application (or a similar one) is still running when it is killed ([discussions.apple.com/thread/254703577](https://discussions.apple.com/thread/254703577)). Reported workarounds include `launchctl unload`/`launchctl disable`, but users consistently report these do not survive reliably — one specifically notes the service "restarts" whenever System Integrity Protection (SIP) is re-enabled, and disabling SIP permanently is the only workaround that "sticks," which is not a supportable posture for ordinary use. No official, SIP-preserving way to permanently disable `ptpcamerad` is documented in this thread or the FAQ/issue sources checked.
- VERIFIED (`mejedi/mac-gphoto-enabler` README): a more surgical alternative to killing the process exists — it patches the per-user SQLite device-discovery database at `~/Library/Caches/com.apple.ImageCaptureNotifications.DeviceDiscoveryDatabase.$UID`, which lists the device rules Image Capture uses to decide which backend (e.g. `PTPCamera`) to auto-launch for a given device; removing/altering the rule for a specific device ID stops the auto-launch for that device without needing `sudo` or SIP changes, and the tool also ships a small daemon so an application can request Fuji-style "no other app touches this device" behavior only while it needs it ([github.com/mejedi/mac-gphoto-enabler](https://github.com/mejedi/mac-gphoto-enabler)). I found no evidence in any source checked of a supported Image Capture preference (e.g. an official "Connecting this camera opens: No application" setting reachable via `defaults`/API) that would achieve the same result without touching this cache database — this looks like an unsupported, reverse-engineered mechanism rather than a documented Apple API.
- VERIFIED (official libusb API documentation, `libusb_reset_device`): the documented contract is "Perform a USB port reset to reinitialize a device... If the reset fails, the descriptors change, or the previous state cannot be restored, the device will appear to be disconnected and reconnected... the device handle is no longer valid... A return code of `LIBUSB_ERROR_NOT_FOUND` indicates when this is the case," and the function is explicitly documented as blocking with "a noticeable delay" ([libusb.sourceforge.io/api-1.0/group__libusb__dev.html](https://libusb.sourceforge.io/api-1.0/group__libusb__dev.html)). The documentation states **no macOS-specific caveat** for this function. Separately, community reports (`libusb/libusb#455` and multiple `libusb-devel` mailing-list threads, surfaced via WebSearch, not independently fetched in full this session) describe `libusb_reset_device` as effectively broken/silently ignored on macOS since El Capitan (10.11) for at least some device classes, and note that a reset-triggered re-enumeration requires the caller to close and reopen the device rather than reuse the old handle. This repository's own observation — a stalled `GetObject` followed by `libusb_reset_device` causing the X-T5 to drop off the bus entirely rather than cleanly re-enumerate — is consistent with this being a real, if inconsistently documented, macOS/libusb interaction rather than a bug specific to this repository's transport code; I found no primary source that fully explains or resolves it, so this remains INFERRED rather than confirmed root-caused.
- VERIFIED (from the same libusb documentation page): no Windows-specific caveat is documented for `libusb_reset_device` either; the only platform caveat on that whole page concerns `libusb_kernel_driver_active` ("This functionality is not available on Windows"), which is unrelated.

- VERIFIED: this repository's `Cargo.toml`/`Cargo.lock` already pin `rusb = "0.9.4"` and `binrw = { version = "0.15.2", ... }`, i.e. it is current with the latest published release of both crates today — there is no version-lag issue for either.
- VERIFIED (`docs/internals/binrw-ptp-migration-research.md`, already in this repository): the `binrw` migration this question asked about was already researched and implemented on 2026-08-29, two days before this research session. That document explicitly reasons through `#[br(count = ...)]`, `parse_with`, and why PTP's length-prefixed (not null-terminated) UTF-16 strings and arrays are kept as a small hand-written codec module (`src/lib/ptp/codec.rs`) rather than mapped onto `binrw`'s `NullWideString`/`NullString`, since those types assume null-termination, which the PTP wire format does not use. Reading `src/lib/ptp/codec.rs` in this session confirms it matches that description: `PtpString`/`PtpExactString`/`PtpArray` are deliberate custom `BinRead`/`BinWrite` implementations with explicit bounds checks (`MAX_PTP_ARRAY_ELEMENTS`, `MAX_PTP_ARRAY_ALLOCATION_BYTES`), not something to further shrink using `binrw` built-ins — no new recommendation is warranted here, and this question is effectively already answered by that document.
- VERIFIED (`rusb` GitHub README, via WebFetch): `rusb` links against C `libusb` — either the system library or a vendored build ("rusb will automatically download the source for libusb and build it" under the `vendored` feature) — and states it is "tested on Linux, OS X, and Windows." I could not determine the exact bundled `libusb` version from the README content fetched.
- VERIFIED (`nusb` docs.rs): `nusb` is "Cross-platform low-level access to USB devices in pure Rust" with backends for Linux (usbfs), **macOS (IOKit)**, Windows (WinUSB), and WebUSB. Its API centers on `MaybeFuture`-returning methods that support both `.wait()` for blocking use and `.await()` in an async context — i.e. it is not async-only, contrary to a common assumption; a fully synchronous call style is available. The typical flow is `list_devices()` → `device_info.open()` → `device.claim_interface(n)` → `interface.endpoint::<Bulk, In>(addr)?.reader()`, using standard `Read`/`Write` traits for transfers. Its own documentation recommends it specifically "to write user-space drivers in Rust for non-standard USB devices" and discourages it for standard USB device classes (mass storage, CDC, HID) — a PTP/MTP camera like the X-T5 is exactly the "non-standard, user-space driver" case it targets.
- VERIFIED (negative result): no PTP crate on crates.io has Fuji-specific knowledge. `ptp` (3drobotics) and `libptp` (a1ien) are both generic PTP/MTP drivers aimed at mass-storage-style devices; neither shows Fuji vendor-extension property codes, opcodes, or the RAW-conversion/backup-restore exchange in their crates.io descriptions, and both are stale (2016 and 2021 respectively). There is nothing here worth borrowing from beyond general PTP container framing, which this repository's own `src/lib/ptp` already implements directly against the spec.

### Post-research reconciliation (this repository's maintainer session)

INFERRED, arithmetic: `libfuji`'s fixed-offset algorithm (values start at absolute offset `0x201`) yields a padding length of `0x201 - (2 + 1 + 2*len(code) + 2)`. For the repository's declared 8-character `"ff179502"` that is `0x1EC`, which contradicts the declared `header_padding: 0x1ee`. But for a **7-character** code it is exactly `0x1EE` — and this repository's own live `GetDevicePropValue(0xD184)` on the X-T5 4.31 decoded to the 7-character pair `"F179502,FA179502"`. The declared `header_padding` is therefore internally consistent with the live D184 reading, and the likeliest single error is a doubled leading `f` in the declared `profile_code` (`"ff179502"` vs the observed `"F179502"`). `libfuji`'s `"FF129504"` captures may simply predate firmware 4.x (their provenance records no firmware version). This narrows candidate 1 to: recapture D185 with a RAF loaded and confirm the embedded code equals D184's first field; do not change `fml/camera.cue` before that capture.
